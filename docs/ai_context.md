## 2. 문제 정의

### 2.1 구체적 장면

12:07, 학생회관 2층. 메뉴는 닭갈비덮밥·미역국·깍두기·요구르트. 유학생 Lina는 메뉴를 번역해 “辣炒鸡肉盖饭”까지는 알지만, 1인분이 몇 g인지, 미역국이 채소인지, 총 칼로리가 얼마인지 모른다. 칼로리 앱을 열어 “닭갈비덮밥”을 검색하면 450~850 kcal가 섞여 나온다. 줄이 다가오고, 결국 감으로 주문한다. 저녁에는 “오늘 좀 많이 먹은 것 같다”만 남는다.

### 2.2 세 가지 마찰

1. **언어 마찰**: 메뉴·영양 정보·1인분 기준이 모두 한국어. 번역은 글자만 해결하고 양은 해결하지 못한다.
2. **구조 마찰**: 한식은 밥+국+반찬+음료의 tray. 기존 앱은 ‘단품’ 기준이라 조합을 다루기 어렵다.
3. **동기 마찰**: 수동 기록은 한 끼 60~90초. 혜택(주간 리포트)은 멀고, 기록은 바로 귀찮다.

### 2.3 왜 지금

- 식약처 K-FIND가 32.7만 건의 식품영양 데이터를 Open API로 제공
- AI Hub/공공데이터로 한식 이미지 학습 데이터 확보 가능
- 대학 캠퍼스 메뉴가 공개 웹페이지로 제공됨
- CLIP/YOLO 계열 추론 비용이 노트북 CPU에서도 가능한 수준

## 3. 솔루션

### 3.1 3단계 흐름

1. **보고 결정한다** — 오늘의 학식 메뉴 + kcal/단백질/나트륨/가격을 먼저 보여준다.
2. **먹고 15초 기록한다** — tray 사진 1장 → 1~3개 음식 인식 → S/M/L 분량 보정 → 저장.
3. **주간 리포트로 행동한다** — 단백질 gap, 나트륨, 7일 streak, 다음 주 액션 3개.

### 3.2 핵심 기능

- 오늘의 학식 메뉴(2개 캠퍼스 × 7일)
- 사진 인식(30개 한식 클래스, Top-3 fallback)
- 다품목 인식(최대 3개, 실제 데모는 1~3개)
- S/M/L 분량 보정(0.75 / 1.0 / 1.25)
- 식사 저장/삭제(SQLite)
- 주간 리포트(단백질·나트륨·streak·인사이트)
- 한/중 이중언어 UI
- FastAPI Swagger 문서
- Android WebView APK

### 3.3 MVP 범위

**Must**
- 2개 캠퍼스 메뉴, 30개 음식 영양 DB
- 사진 1장 → 1~3개 인식
- 분량 보정 + 저장
- 주간 리포트
- 한/중 이중언어

**Should**
- Top-3 fallback
- 관리자용 메뉴 갱신
- APK 패키징

**Won’t (이번 MVP에서 안 함)**
- 의료 진단/질환 관리
- 1,000종 이상 음식
- 그램 단위 정확한 분량
- 소셜/랭킹/식단 처방
- 오프라인 AI(모델을 APK에 내장하지 않음)

## 4. 실제 구현 상태 (가장 중요)

### 4.1 AI

- 모델: `openai/clip-vit-base-patch32` (zero-shot CLIP)
- 클래스: 30개 한식
- 방식: 이미지 임베딩 ↔ 30개 클래스 텍스트 프롬프트 유사도 → softmax → Top-5
- 다품목: 전체 이미지 1장 + 4개 영역 crop(left/right/top/bottom) → 최대 3개 unique
- 분량: S=0.75, M=1.0, L=1.25 (그램 추정 아님)
- CPU 추론: 약 0.35~0.45초/장 (로컬), 터널 경유 약 0.9초
- 샘플 3장 결과:
  - 비빔밥 0.968
  - 김치찌개 0.546 (2위 순두부찌개 0.187)
  - 돈까스 0.844

> **한계**: zero-shot이라 실제 급식 tray에서의 정확도는 검증되지 않았다. 샘플 3장 Top-1 3/3은 “데모가 동작한다”는 뜻이지 “정확도 80%”가 아니다. 다품목도 항상 3~5개를 찾는 것이 아니라, 대부분 1개가 나온다.

### 4.2 API

| Method | Endpoint | 설명 |
|---|---|---|
| GET | `/api/health` | 서버/AI 상태 |
| GET | `/api/menu/today?campus=student` | 오늘의 학식 |
| POST | `/api/predict` | 이미지 → 음식 인식 |
| GET | `/api/nutrition/{food_id}` | 음식 영양 |
| GET | `/api/meals?day=YYYY-MM-DD` | 하루 기록 |
| GET | `/api/meals/week` | 주간 기록 |
| POST | `/api/meals` | 식사 저장 |
| DELETE | `/api/meals/{id}` | 식사 삭제 |
| GET | `/api/report/week` | 주간 리포트 |
| GET/PUT | `/api/profile` | 목표/캠퍼스 |
| GET | `/docs` | Swagger |

### 4.3 DB/프론트/APK

- SQLite: `meals`, `meal_items`, `profile`
- 첫 실행 시 7일 demo seed(하루 1끼, 총 7끼) → 리포트가 비어 있지 않음
- 프론트: vanilla HTML/CSS/JS PWA, 3개 화면(오늘/기록/리포트), 한/중 토글
- APK: Android WebView, `com.hankki.ai`, minSdk 24, targetSdk 35, 약 17KB
- APK는 **서버 URL을 로드하는 껍데기**이며, 오프라인 AI가 아니다.

### 4.4 아직 안 된 것

- K-FIND serviceKey 연동 (현재 30종 로컬 baseline)
- 실제 tray 2,000~3,000장 라벨링/파인튜닝
- YOLO detector + EfficientNet classifier (계획만)
- 사용자 60명 설문/10명 인터뷰/15명 일지 (계획만)
- 로그인/멀티유저
- Play Store 정식 배포
- 오프라인 APK

## 7. 팀 구성과 RACI

| 역할 | 담당 |
|---|---|
| A | AI/데이터: 라벨링, CLIP/YOLO 학습, 평가 |
| B | 백엔드/영양: FastAPI, SQLite, K-FIND, 메뉴 수집 |
| C | 프론트/디자인: PWA, 3화면, 차트, 한/중 |
| D | PM/QA/문서: 조사, 테스트, 배포, HWP/PPT, 데모 |

| 업무 | A | B | C | D |
|---|---|---|---|---|
| AI 인식 | R/A | C | I | C |
| 백엔드/영양 | C | R/A | I | C |
| 프론트/디자인 | I | C | R/A | C |
| 테스트/배포 | C | C | C | R/A |
| 문서/발표 | C | C | C | R/A |
| 프로젝트/조사 | C | I | C | R/A |

> A/B/C/D는 역할 표시입니다. 실제 이름은 `[팀원 1]`~`[팀원 4]`로 바꿔야 합니다.

## 8. 검증 지표

### 8.1 목표

| 구분 | 지표 | 목표 |
|---|---|---|
| 모델 | Top-1 | ≥ 80% |
| 모델 | Top-3 | ≥ 92% |
| 모델 | CPU 추론 | ≤ 1.5초 |
| 제품 | 한 끼 기록 시간 | ≤ 15초 |
| 제품 | 사진 기록 비중 | ≥ 60% |
| 제품 | D7 리텐션 | ≥ 30% |
| 제품 | D30 리텐션 | ≥ 20% |
| 제품 | SUS | ≥ 70 |
| 비즈니스 | 유료 전환 의향 | ≥ 5% |
| 비즈니스 | 교내 협력 | ≥ 2곳 |

### 8.2 현재까지 확인한 것

- 샘플 3장 Top-1 3/3 (일반화 성능 아님)
- end-to-end 저장/리포트 동작
- API `/docs` 동작
- APK 빌드/서명 완료
- 실제 사용자 테스트는 아직 없음

### 8.3 중단/전환 조건

- Top-1 < 65% 또는 D7 < 15% → 1개 캠퍼스로 축소, 메뉴/수동 기록 중심으로 전환
- Top-1 65~80% + 메뉴 선호가 더 강함 → “캠퍼스 메뉴 영양 도우미”로 피벗
- Top-1 ≥ 80%, D7 ≥ 30% → 5개 캠퍼스로 확장

### 10.2 추진배경 (복사용)

한국 대학 캠퍼스에서 식사하는 외국인 유학생은 학식 메뉴의 한국어 설명과 1인분 양을 이해하기 어려워 영양 관리가 사실상 불가능하다. 기존 칼로리 앱은 서구권 단품 중심이라 밥·국·반찬으로 구성된 한식 tray를 제대로 다루지 못하고, 수동 검색은 한 끼에 60~90초가 걸려 지속하기 어렵다. 2026년 기준 재한 외국인 유학생은 30.7만 명, 중국인 유학생은 7.89만 명으로 늘었지만 이들을 위한 캠퍼스 특화 식단관리 서비스는 없다. 이에 본 프로젝트는 ‘먹기 전 메뉴 확인 → 먹은 후 사진 한 장 기록 → 주간 리포트’를 15초 안에 완결하는 AI 식단관리 MVP를 개발했다.

### 10.3 목표 및 내용 (복사용)

1. 30개 한식 클래스를 zero-shot으로 인식하고, 5개 영역 crop과 Top-3 fallback으로 오인식에 대응한다.
2. 2개 캠퍼스 × 7일 학식 메뉴와 30개 음식 영양 DB를 제공한다.
3. 사진 1장에서 1~3개 음식을 인식하고, 사용자가 S/M/L로 분량을 보정한 뒤 SQLite에 저장한다.
4. 주간 리포트에서 단백질 gap, 나트륨, 7일 streak, 다음 행동 3개를 제안한다.
5. FastAPI 10개 endpoint + Swagger + 설치형 PWA/Android WebView로 실제 실행 가능한 형태를 만든다.

### 10.4 수행결과 (복사용)

- CLIP zero-shot 30클래스, CPU 약 0.4초, 샘플 3장 기준 Top-1 3/3을 확인했다.
- FastAPI + SQLite + PWA가 실제로 동작하며, /docs에서 API를 직접 호출할 수 있다.
- 사진 업로드 → 인식 → 분량 보정 → 저장 → 주간 리포트까지 end-to-end로 검증했다.
- Android WebView 기반 APK(HankkiAI-debug.apk)를 빌드해 설치 가능한 실행 패키지를 만들었다.
- 한계: zero-shot 정확도는 실제 tray에서 추가 학습이 필요하고, K-FIND serviceKey는 아직 연동하지 않아 30개 로컬 baseline을 사용한다.

SW중심대학 마이크로스톤 프로젝트에서 `[역할]`을 맡아 문제 정의, 4인 RACI, 8주 일정, 사용자 조사 설계(60명), FastAPI/SQLite 백엔드, Android 실행 패키지, 발표자료 구조화까지 완성했습니다. 특히 CLIP zero-shot + FastAPI + PWA를 8주 안에 실제 동작하는 MVP로 구현하고, 사진 업로드→인식→저장→주간 리포트의 전체 흐름을 검증했습니다. 단순한 아이디어 제안이 아니라 설치 가능한 APK와 API 문서까지 결과물로 남겼고, 팀원 4명의 역할을 RACI로 정리해 일정 안에 협업했습니다. 이 경험을 바탕으로 SW중심대학 장학생으로서 다음 단계(실제 tray 데이터 학습, K-FIND 연동)까지 이어가고 싶습니다.
